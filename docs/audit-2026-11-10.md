# Project 180: full audit

Date: 10 November 2026. Scope: the whole repo as it is on disk (one commit plus 24 uncommitted files).

## How this was done, and what it doesn't cover

- I read all of `packages/api/src`, the database schema, the validators, both Worker configs, the test list, and the config files.
- For the two apps I read the key files (API client, `main.tsx`, Vite and PWA config) and searched every file for breaks of the rules in `CLAUDE.md`. I did not read all 27,000 lines of UI code.
- **Nothing was run.** Biome, the type check and the tests can't run in the shell I had. Every finding comes from reading the code, so treat the bugs as "very likely" until a test confirms them.
- I did not look at any screen in a browser, so layout, dark mode and 375px checks are not covered.
- I did not check the seed data or the 221 exercise photo folders against their licences.

## Summary

The project is in good shape for its size. Access control is the strongest part: every personal route uses `requireUser`, staff routes go through `managedPerson` / `managedUsers`, other people's data answers 404, and the tests cover most of it. I found no way for a client to read another client's data, and no way for a coach to reach another coach's clients.

The things worth fixing first:

| # | Finding | Severity |
|---|---------|----------|
| 1 | Dashboard overview runs about 6 database queries per client, one client at a time | High |
| 2 | Temporary passwords are easy to guess and never expire | High |
| 3 | A finished workout can still be changed or "finished" again | Medium |
| 4 | Adding a client with a bad program leaves a half-made account | Medium |
| 5 | No way to delete a person's account or data, though the welcome email offers it | Medium |
| 6 | Temporary passwords are written to the logs when email keys are missing | Medium |
| 7 | One commit, 24 uncommitted files, no CI | Medium |
| 8 | No CSRF check on our own routes; no Content-Security-Policy | Medium |
| 9 | Live database id is still a placeholder | Before go-live |

Everything else is low severity and listed further down.

## High

### 1. The dashboard overview will stop working as clients are added

`packages/api/src/routes/admin-overview.ts` line 93 loops over every client and calls `buildPlan` for each, waiting for one before starting the next. `buildPlan` (`routes/me.ts`) runs up to 6 queries per client.

- Cloudflare D1 allows 50 queries per request on the free plan and 1,000 on the paid plan. With about 8 clients on a program, the overview passes 50 and the request fails. On the paid plan the limit is around 160 clients.
- Before it fails it gets slow: 30 clients is roughly 180 database round trips, one after another.
- This also breaks two project rules: run independent reads with `Promise.all`, and aggregate in SQL.

Fix: load all active enrollments, program days and completed sessions for the managed clients in three or four queries, then build each calendar in memory. `buildProgramCalendar` already takes plain data, so the change is in the loading code only.

The same pattern, smaller, is in `pastPrograms` (`routes/admin-users.ts`): four queries per past program, in a loop.

### 2. Temporary passwords are weak and never expire

- The new-client wizard (`apps/admin/src/components/new-client-wizard.tsx` line 52) makes passwords like `Tempo-Climb-47` from a list of 12 words: 12 × 12 × 90 = **12,960 possible passwords**, picked with `Math.random()`.
- The sign-in limit allows 5 tries per email every 15 minutes, which is 480 a day. Someone who knows a client's email can expect to guess a temporary password in about two weeks.
- A temporary password stays valid until the client signs in. A client who never opens the app keeps a guessable password for ever.
- The password is sent by email in plain text. That is by design, but it makes the two points above matter more.

Fix:
1. Generate with `crypto.getRandomValues` and a much longer word list (or 4 words). Aim for at least 40 bits.
2. Store when the temporary password was set and refuse sign-in after, say, 7 days ("ask your coach for a new one").
3. Longer term: email a one-time "choose your password" link instead of the password itself.

## Medium

### 3. A finished workout can still be changed

`CLAUDE.md` says a finished session can't be reopened. The API doesn't enforce it (`routes/sessions.ts`):

- `POST /sessions/:id/finish` has no status check. Calling it on a session that is already completed or abandoned rewrites `endedAt` and recalculates the duration from the original start time to now. An abandoned session from last week can be flipped to "completed" with a duration of seven days, and that then counts in stats and records.
- `PUT /sessions/:id/sets` and `DELETE /sessions/:id/sets/:clientUuid` also have no status check, so sets can be added, changed or removed after the workout is finished.
- Only `restart` checks for `in_progress`.

The phone app doesn't do any of this on purpose, but a retried request or a second tab can. Fix: answer 409 on `finish` unless the session is `in_progress` (or return the existing result if it is already completed, so a retry is safe), and refuse set changes on finished sessions. Add a test for each.

### 4. Adding a client can leave a half-made account

`POST /admin/users` creates the account, then the profile, then the weigh-in, then assigns the program. If the program can't be found or isn't visible to that coach, the request fails with 404 after the account already exists. The coach sees an error, tries again, and gets "That email already has an account".

Fix: check the program (and the coach id) before creating the user. Nothing here runs in one batch, so the order is the only protection.

The same applies in a smaller way to `copyProgramForClient`: it copies each workout one at a time, so a failure half-way leaves orphan workout copies. It also costs about 5 round trips per workout, so assigning a program with 12 workouts is about 60 queries, which is over the free-plan limit in finding 1.

### 5. No way to delete a person

There is no endpoint to delete or deactivate an account. The welcome email tells clients "Ask your coach if you'd like it removed", and POPIA gives them that right, but a coach has no button for it. Today it would need hand-written SQL, and several foreign keys (`enrollments.assigned_by`, `created_by` on library rows) would block a plain delete.

Fix: add an owner-only "Delete this person and everything they logged" action behind `ConfirmDialog`, with a privacy test. Decide what happens to a coach's library items when a coach is removed (hand them to an owner).

### 6. Temporary passwords can end up in the logs

`sendEmail` (`packages/api/src/email.ts`) logs the full text of the email when the AWS keys are missing. For welcome and reset emails that text includes the temporary password. Both Workers have `observability` on, so if the live site ever runs without the keys, passwords are stored in Cloudflare's logs.

Fix: log the recipient and subject only, as the "test site" branch already does.

### 7. Version control and checks

- The whole history is one commit. 24 files are changed or new and not committed, including the admin PWA work and today's fixes. A disk problem loses all of it.
- There is no CI (no `.github/workflows`). The pre-commit hook runs Biome and the type check but not the tests, which is how the stale `distanceM` test got through.
- Deploy does not run migrations. The README says to run `db:migrate:dev` by hand first; forgetting it ships code against an old schema.

Fix: commit in small steps, add a GitHub Action that runs `bun run check` on every push, and make the deploy script run the migration first.

### 8. Browser-side protections

- **CSRF.** Our own routes read JSON with `req.json()` whatever the content type, and there is no `Origin` check. What protects them today is Better Auth's default `SameSite=Lax` cookie. That is a reasonable protection but it is the only one. Adding Hono's `csrf()` middleware (an Origin check) on `/api/*` is a few lines.
- **No Content-Security-Policy** in either `_headers` file, and no `Strict-Transport-Security`. The apps have no `dangerouslySetInnerHTML`, so the risk is low, but a CSP limits the damage of any future mistake. It needs to allow Google Fonts and the YouTube embed.
- API responses carry no security headers (`secureHeaders()` from Hono would add them).

### 9. Before go-live

- `database_id` for the live database is `00000000-0000-0000-0000-000000000000` in both `wrangler.jsonc` files. The live site has not been set up yet; this is a reminder, not a bug.
- Both apps load fonts from Google's servers. The first load on a new phone with no signal has no fonts, and Google sees each client's IP address. Self-hosting the two fonts fixes both.

## Low

### API and data

- **Deleting an exercise for good can fail with a 500.** `usageOf` checks `workout_exercises` and `set_logs` but not `session_exercises`. If a session was started with the exercise and no set was logged, the foreign key blocks the delete and the coach sees "Something went wrong". Count `session_exercises` too.
- **Sign-in limit.** The check and the count are separate steps, so several requests sent at the same moment can all get through before the lock. Anyone can also lock a known email for 15 minutes with 5 wrong tries (a trade-off of this design). Rows in `sign_in_attempts` are never cleaned up.
- **Missing indexes.** `workout_sessions.enrollment_id` and `enrollments.program_id` are filtered on in the progress, reset and purge queries but have no index. `session_exercises.exercise_id` has none either. Not noticeable yet; it will be once there is a year of sessions.
- **Sequential reads.** `GET /admin/users/:id/progress`, `/activity`, `enrollmentImpact`, `loadProfile` and `historyCounts` each run 2 to 4 independent queries one after another. The project rule is `Promise.all`.
- **Every request reads the session from D1.** Better Auth's `cookieCache` is off. Turning it on (a few minutes' cache) removes one or two queries from every API call.
- **YouTube quota.** `GET /videos` is open to any signed-in user for any exercise id. A client could walk through the ids and use up the day's 100 searches. Limit it to exercises in their own plan, or to staff.
- **Loose validation.** Dates are checked by shape only (`2026-13-45` passes). `PATCH /me` lets a client change their time zone and weight unit, which the project says never change. `videoUrl` accepts any URL scheme; React 19 blocks `javascript:` links, but the validator should only allow `https` YouTube or Vimeo links. `programDayId` on a new session isn't checked against the person's program.
- **Weigh-ins.** `PUT /me/checkins` with a `clientUuid` that was already used for another date fails with a 500 (unique index) instead of a clear message.
- **Dead or stale code.** `assertMayWipe` in `purge.ts` can never refuse (the routes are staff-only already). The comment on `DELETE /workouts/:id/permanent` says program days become rest days; the code refuses with 409 instead. `env.ts` still mentions `apps/web`. The test email in `admin-email.ts` puts the name into HTML without escaping.

### Project rules broken in the apps

- **`await invalidateQueries` before leaving or closing** (rule: never; use `void`): 14 places in the admin, including the workout and program editors' save, duplicate and archive actions, the new-client wizard, the coach picker, the exercise delete dialog and both video dialogs. Each makes the screen wait for a full reload.
- **A bare `<select>`** in the program grid (`programs_.$programId.tsx` line 422). The rule is to always use `Select`. If the compact grid cell needs a special case, say so in `CLAUDE.md`.
- **Bare `<input>`** in the phone app's weigh-in (`weigh-in.tsx`) and set entry (`workout.$sessionId.tsx` line 1044) instead of `Field` + `Input`. Both do set `inputMode`.
- **Hard-coded colours** other than the two allowed: lime `#b6e63b` in `celebration.tsx`, `interval-timer.tsx` and `auth-shell.tsx`; steel `#7aa2c2` in `interval-timer.tsx`; sand `#dcb46a` in `celebration.tsx`. Use the tokens.
- **The phone app mentions the admin.** `apps/app/src/urls.ts` exports `ADMIN_URL` and the app's `.env` files set `VITE_ADMIN_URL`. Nothing imports it, so it doesn't reach users, but the rule is that nothing in `apps/app` hints at the admin. Delete the file and the variable.
- **Role checks** use `u.role === 'member'` in `users.tsx` and the wizard. The rule names `role === 'admin'` specifically, so this is borderline; an `isClient` helper in shared would keep it consistent.

### Maintainability

- Two files are very large: the admin workout editor (1,446 lines) and the phone workout screen (1,205 lines). They are the two most important screens and the hardest to change safely. Split each into the screen, its hooks (draft, sync, timers) and its row components.
- `packages/client` and `packages/ui` have no tests. The offline set queue (`flushSets`, the local board in `localStorage`) is the riskiest client code and has none.
- On a 401 the app clears local data, including a workout's unsaved local board. With 30-day sliding sessions this is rare, but a client signed out from the admin mid-workout loses unsynced sets.

### Tests

- 74 API tests and 5 shared test files; coverage of access rules is good.
- Missing privacy tests (the rule asks for one per resource): body check-ins, `/me/stats`, `/videos`.
- Missing behaviour tests: finishing twice, changing sets after finishing (finding 3), the half-made client (finding 4), the D1 100-value limit on a full 52-week program.
- End-to-end: one smoke file with 3 checks for the phone app, none for the admin. No test signs in and logs a workout through the real screens.
- Changed today: `vitest.config.ts` now ignores Better Auth's two expected errors (wrong password, sign-up disabled) when they show up as unhandled rejections. Any other unhandled error still fails the run.

## What is done well

- Access rules live in two small files (`access.ts`, `library.ts`) and every route uses them. "Not yours" answers 404, so ids reveal nothing.
- No public sign-up, a sign-in limit, sliding sessions, forced password change with other devices signed out, and the guard that blocks every route until the password is chosen.
- Client copies of programs and the per-session snapshot of targets keep history correct when the library changes.
- `insertMany` / `runAll` handle D1's 100-value limit in one place; writes that belong together are batched.
- Email has three layers of protection against mailing real people from dev, each with a test.
- Uploads are limited by type and size, stored under random keys, and served with `nosniff`.
- Validation is in one shared file used by both the API and the forms.
- No `dangerouslySetInnerHTML`, no `any`, no `@ts-ignore`, no `window.confirm`, no `<input type="date">`, no bare password inputs, no stray `console.log` in the apps.
- Secrets are not in the repo; `.dev.vars` is ignored and only an example is committed.

## Suggested order

1. Commit what is on disk and add CI (finding 7). It protects everything after it.
2. Temporary passwords: stronger generator, expiry, stop logging them (findings 2 and 6).
3. Lock finished sessions (finding 3) and reorder client creation (finding 4), each with a test.
4. Rewrite the overview query (finding 1) before the client list grows.
5. Delete-a-person action (finding 5) and the CSRF and CSP headers (finding 8) before go-live.
6. Work through the low list as the files are touched.
