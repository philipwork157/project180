## High

### 1. The dashboard overview will stop working as clients are added: DONE (12 Nov 2026)

**What was done:**

- `buildPlans(db, people)` in `routes/me.ts` loads every client's plan in a fixed number of queries (active enrollments, then program days + completed sessions together, then workout names + exercise counts together). `buildPlan` now calls it for one person.
- `admin-overview.ts` runs all its independent reads in one `Promise.all` (sessions, app time summed in SQL, plans, recent workouts, library counts, enrollment count). About 10 queries in total, whatever the number of clients.
- `inChunks` (`batch.ts`) splits id lists so no statement goes over D1's 100 bound values, which the old `inArray(ids)` calls would have hit at 100+ clients.
- `pastPrograms` (`admin-users.ts`) loads every past program's history in one go, and `enrollmentImpacts` counts sessions, sets and weigh-ins for all of them in three grouped queries. The progress route runs the current plan and past programs side by side.
- Not yet verified by running: `bun run check` couldn't run in the shell used (macOS-only binaries). Run it before committing.

`packages/api/src/routes/admin-overview.ts` line 93 loops over every client and calls `buildPlan` for each, waiting for one before starting the next. `buildPlan` (`routes/me.ts`) runs up to 6 queries per client.

- Cloudflare D1 allows 50 queries per request on the free plan and 1,000 on the paid plan. With about 8 clients on a program, the overview passes 50 and the request fails. On the paid plan the limit is around 160 clients.
- Before it fails it gets slow: 30 clients is roughly 180 database round trips, one after another.
- This also breaks two project rules: run independent reads with `Promise.all`, and aggregate in SQL.

Fix: load all active enrollments, program days and completed sessions for the managed clients in three or four queries, then build each calendar in memory. `buildProgramCalendar` already takes plain data, so the change is in the loading code only.

The same pattern, smaller, is in `pastPrograms` (`routes/admin-users.ts`): four queries per past program, in a loop.

### 2. Temporary passwords are weak and never expire: DONE (12 Nov 2026), points 1 and 2

**What was done:**

- `generateTempPassword()` in `packages/shared/src/passwords.ts`: 4 words from a 256-word list plus a 3-digit number (e.g. `Savanna-Berry-Turtle-Chalk-679`), drawn with `crypto.getRandomValues` with no modulo bias. About 41.8 bits, up from about 13.7. Unit tests in `passwords.test.ts`.
- The new-client wizard uses it, and the coach's "Set a temporary password" drawer now pre-fills one with a New button (it used to start empty, so coaches typed their own).
- Temporary passwords stop working after `TEMP_PASSWORD_DAYS` (7). The sign-in route (`packages/api/src/index.ts` + `temp-password.ts`) checks, after a right password, whether it is still temporary and was set more than 7 days ago (the credential account's `updated_at`, which only changes when the password does). If so it deletes their sessions and answers 403 `TEMP_PASSWORD_EXPIRED`: "Ask your coach for a new one". A wrong password still answers 401, so this tells a stranger nothing. No schema change was needed.
- The welcome and new-password emails say the temporary password works for 7 days, and the dashboard overview's "needs attention" list says "Temporary password expired: set a new one".
- Tests in `security.test.ts`: works at 6 days, refused at 8 with no session left, wrong password still 401, a reset starts a fresh week, a chosen password never expires.
- Still open: point 3 (email a one-time link instead of the password). Finding 6 (passwords in logs) is separate and still open.

- The new-client wizard (`apps/admin/src/components/new-client-wizard.tsx` line 52) makes passwords like `Tempo-Climb-47` from a list of 12 words: 12 × 12 × 90 = **12,960 possible passwords**, picked with `Math.random()`.
- The sign-in limit allows 5 tries per email every 15 minutes, which is 480 a day. Someone who knows a client's email can expect to guess a temporary password in about two weeks.
- A temporary password stays valid until the client signs in. A client who never opens the app keeps a guessable password for ever.
- The password is sent by email in plain text. That is by design, but it makes the two points above matter more.

Fix:

1. Generate with `crypto.getRandomValues` and a much longer word list (or 4 words). Aim for at least 40 bits.
2. Store when the temporary password was set and refuse sign-in after, say, 7 days ("ask your coach for a new one").
3. Longer term: email a one-time "choose your password" link instead of the password itself.

## Medium

### 3. A finished workout can still be changed: DONE (12 Nov 2026)

**What was done:**

- `assertInProgress` in `routes/sessions.ts` answers 409 "This workout is already finished" for `PUT /sessions/:id/sets`, `DELETE /sessions/:id/sets/:clientUuid`, `restart` and `swap` on a finished or abandoned workout.
- `finish` only updates a session that is still `in_progress` (checked inside the UPDATE, so two at once can't both win). A retried "completed" on a completed session gets the same answer again and changes nothing; anything else answers 409. An abandoned workout can no longer be turned into a 7-day "completed" one.
- The phone app treats a 409 on saving a set as final, so it stops retrying every 8 seconds.
- Test in `flow.test.ts`: add, change and delete refused, a retried finish keeps the original feeling and time, abandoned-then-completed refused.

`CLAUDE.md` says a finished session can't be reopened. The API doesn't enforce it (`routes/sessions.ts`):

- `POST /sessions/:id/finish` has no status check. Calling it on a session that is already completed or abandoned rewrites `endedAt` and recalculates the duration from the original start time to now. An abandoned session from last week can be flipped to "completed" with a duration of seven days, and that then counts in stats and records.
- `PUT /sessions/:id/sets` and `DELETE /sessions/:id/sets/:clientUuid` also have no status check, so sets can be added, changed or removed after the workout is finished.
- Only `restart` checks for `in_progress`.

The phone app doesn't do any of this on purpose, but a retried request or a second tab can. Fix: answer 409 on `finish` unless the session is `in_progress` (or return the existing result if it is already completed, so a retry is safe), and refuse set changes on finished sessions. Add a test for each.

### 4. Adding a client can leave a half-made account: DONE (12 Nov 2026)

**What was done:** `POST /admin/users` now checks the program (visible to this coach, not archived), the chosen coach and the email together, before creating anything. A refusal leaves no account, so trying again works. Test in `profiles-email.test.ts`.

**Program copies (done later the same day):** `copyProgramForClient` reads the program, its days, workouts, rows and groups up front, creates the program and workout copies in one batch, then fills them in a second batch. If the second batch fails, the first is undone, so no empty copies are left behind. That is about 6 round trips whatever the program size (it was about 5 per workout, so a 12-workout program went over the free plan's 50-query limit). Test in `coaching.test.ts` (4 weeks, 2 workouts reused, a superset group). The two other loops that copy workouts one by one while syncing copies (`programs.ts`, added with the sync work) still do; worth the same treatment once that work settles.

`POST /admin/users` creates the account, then the profile, then the weigh-in, then assigns the program. If the program can't be found or isn't visible to that coach, the request fails with 404 after the account already exists. The coach sees an error, tries again, and gets "That email already has an account".

Fix: check the program (and the coach id) before creating the user. Nothing here runs in one batch, so the order is the only protection.

The same applies in a smaller way to `copyProgramForClient`: it copies each workout one at a time, so a failure half-way leaves orphan workout copies. It also costs about 5 round trips per workout, so assigning a program with 12 workouts is about 60 queries, which is over the free-plan limit in finding 1.

### 5. No way to delete a person: DONE (12 Nov 2026)

**What was done:** `DELETE /admin/users/:id` (owners only; never yourself or another owner). One D1 batch, so all of it happens or none of it:

- A coach's clients, exercises, workouts, programs and swap suggestions are handed to the owner doing it; `enrollments.assigned_by` pointing at them is cleared.
- The person's sessions (with sets and snapshots), weigh-ins, app activity, enrollments, their own program and workout copies, sign-in attempts, and finally the user (sign-ins, devices and profile cascade).
- The Users page has a delete IconButton for owners, behind `ConfirmDialog`, with a toast saying what was removed or handed over.
- Tests in `coaching.test.ts`: only owners, not yourself, nothing left in any table for a deleted client, a coach's clients and library move to the owner.

There is no endpoint to delete or deactivate an account. The welcome email tells clients "Ask your coach if you'd like it removed", and POPIA gives them that right, but a coach has no button for it. Today it would need hand-written SQL, and several foreign keys (`enrollments.assigned_by`, `created_by` on library rows) would block a plain delete.

Fix: add an owner-only "Delete this person and everything they logged" action behind `ConfirmDialog`, with a privacy test. Decide what happens to a coach's library items when a coach is removed (hand them to an owner).

### 6. Temporary passwords can end up in the logs: DONE (12 Nov 2026)

**What was done:** with no AWS keys, `sendEmail` logs the recipient and subject only, never the body. Test in `profiles-email.test.ts` checks that a password in the body never reaches `console.log` in any mode.

`sendEmail` (`packages/api/src/email.ts`) logs the full text of the email when the AWS keys are missing. For welcome and reset emails that text includes the temporary password. Both Workers have `observability` on, so if the live site ever runs without the keys, passwords are stored in Cloudflare's logs.

Fix: log the recipient and subject only, as the "test site" branch already does.

### 8. Browser-side protections: DONE (12 Nov 2026)

**What was done:**

- **CSRF:** Hono's `csrf()` runs on every `/api` route (`packages/api/src/index.ts`). A form or text/plain POST is refused with 403 unless it comes from our own address, `BETTER_AUTH_URL` or `TRUSTED_ORIGINS` (so the admin dev server on :5174 still works). JSON from other sites was already blocked by CORS.
- **API headers:** `secureHeaders()` on every answer (nosniff, HSTS for a year, `default-src 'none'`, no framing). Cross-Origin-Resource-Policy is left off because the admin shows photos from the phone app's address.
- **Content-Security-Policy and HSTS** in both `public/_headers`. Scripts, styles and fonts only from our own origin (fonts are now bundled, see finding 9); frames only YouTube (nocookie) and Vimeo; images also from YouTube thumbnails, and in the admin from the phone app's live and dev addresses. HSTS is one year, without `includeSubDomains` (other subdomains may not all be HTTPS).
- The inline theme script in both `index.html` files moved to `public/theme.js`, so the CSP can forbid inline scripts.
- Tests in `security.test.ts`: a cross-site form POST is refused with a valid cookie, our own works, and the headers are present.
- **Check after the next deploy:** open both sites with the browser console open and look for CSP errors. Two things to watch: Cloudflare features that inject scripts (Web Analytics, Rocket Loader, email obfuscation) need their host added or must be off, and Zod may log one harmless CSP message when it checks whether it can use `eval`.

- **CSRF.** Our own routes read JSON with `req.json()` whatever the content type, and there is no `Origin` check. What protects them today is Better Auth's default `SameSite=Lax` cookie. That is a reasonable protection but it is the only one. Adding Hono's `csrf()` middleware (an Origin check) on `/api/*` is a few lines.
- **No Content-Security-Policy** in either `_headers` file, and no `Strict-Transport-Security`. The apps have no `dangerouslySetInnerHTML`, so the risk is low, but a CSP limits the damage of any future mistake. It needs to allow Google Fonts and the YouTube embed.
- API responses carry no security headers (`secureHeaders()` from Hono would add them).

### 9. Before go-live: fonts DONE (12 Nov 2026)

**What was done:** Archivo and Plus Jakarta Sans are bundled with `@fontsource` (only the weights in use, imported in each app's `main.tsx`), and the Google Fonts links, preconnects, CSP hosts and service-worker cache rule are gone. The Latin font files are precached, so a new phone has the fonts offline and Google never sees a client's IP. Needs `bun install` once.

- Both apps load fonts from Google's servers. The first load on a new phone with no signal has no fonts, and Google sees each client's IP address. Self-hosting the two fonts fixes both.

## Low

### API and data

- **Deleting an exercise for good can fail with a 500.** `usageOf` checks `workout_exercises` and `set_logs` but not `session_exercises`. If a session was started with the exercise and no set was logged, the foreign key blocks the delete and the coach sees "Something went wrong". Count `session_exercises` too. **Done 12 Nov:** the delete checks past-workout snapshots (also swapped-from), and the dialog now says "in N past workouts" and offers Archive instead of failing.
- **Sign-in limit.** The check and the count are separate steps, so several requests sent at the same moment can all get through before the lock. Anyone can also lock a known email for 15 minutes with 5 wrong tries (a trade-off of this design). Rows in `sign_in_attempts` are never cleaned up.
- **Missing indexes.** `workout_sessions.enrollment_id` and `enrollments.program_id` are filtered on in the progress, reset and purge queries but have no index. `session_exercises.exercise_id` has none either. Not noticeable yet; it will be once there is a year of sessions. **Done 12 Nov:** all three (and a few more) in migration 0010.
- **Sequential reads.** `GET /admin/users/:id/progress`, `/activity`, `enrollmentImpact`, `loadProfile` and `historyCounts` each run 2 to 4 independent queries one after another. The project rule is `Promise.all`.
- **Every request reads the session from D1.** Better Auth's `cookieCache` is off. Turning it on (a few minutes' cache) removes one or two queries from every API call.
- **YouTube quota.** `GET /videos` is open to any signed-in user for any exercise id. A client could walk through the ids and use up the day's 100 searches. Limit it to exercises in their own plan, or to staff. **Done 12 Nov:** staff may look up any exercise; a client only exercises in their own program copies or workouts they've started (else 404). Test in `security.test.ts`.
- **Loose validation.** Dates are checked by shape only (`2026-13-45` passes). `PATCH /me` lets a client change their time zone and weight unit, which the project says never change. `videoUrl` accepts any URL scheme; React 19 blocks `javascript:` links, but the validator should only allow `https` YouTube or Vimeo links. `programDayId` on a new session isn't checked against the person's program. **Done 12 Nov:** dates must exist (`isoDate` in shared, used everywhere); `PATCH /me` only takes the name; `videoUrl` must be an https YouTube or Vimeo link; `programDayId` must be a day of your own (given or current) program. Tests in `validators.test.ts` and `security.test.ts`.
- **Weigh-ins.** `PUT /me/checkins` with a `clientUuid` that was already used for another date fails with a 500 (unique index) instead of a clear message. **Done 12 Nov:** answers 409 "Weigh-in id in use" and changes nothing.
- **Dead or stale code.** `assertMayWipe` in `purge.ts` can never refuse (the routes are staff-only already). The comment on `DELETE /workouts/:id/permanent` says program days become rest days; the code refuses with 409 instead. `env.ts` still mentions `apps/web`. The test email in `admin-email.ts` puts the name into HTML without escaping. **Done 13 Nov:** all four fixed (`assertMayWipe` removed, comments corrected, name escaped).

Each makes the screen wait for a full reload. **Done 12 Nov:** all of them (and five more hidden in `Promise.all`) now refresh in the background with `void`; exercise saves, photos, videos and the coach picker also update the cache from the server's reply (`putExercise` in packages/client), so nothing shows stale.
- **A bare `<select>`** in the program grid (`programs_.$programId.tsx` line 422). The rule is to always use `Select`. - **Bare `<input>`** in the phone app's weigh-in (`weigh-in.tsx`) and set entry (`workout.$sessionId.tsx` line 1044) instead of `Field` + `Input`. Both do set `inputMode`. **Done 13 Nov:** set entry and the weigh-in sheet use `Input`; the old unused `weigh-in.tsx` is deleted.

## What is done well

- Access rules live in two small files (`access.ts`, `library.ts`) and every route uses them. "Not yours" answers 404, so ids reveal nothing.
- No public sign-up, a sign-in limit, sliding sessions, forced password change with other devices signed out, and the guard that blocks every route until the password is chosen.
- Client copies of programs and the per-session snapshot of targets keep history correct when the library changes.
- `insertMany` / `runAll` handle D1's 100-value limit in one place; writes that belong together are batched.
- Email has three layers of protection against mailing real people from dev, each with a test.
- Uploads are limited by type and size, stored under random keys, and served with `nosniff`.
- Validation is in one shared file used by both the API and the forms.
- No `dangerouslySetInnerHTML`, no `any`, no `@ts-ignore`, no `window.confirm`, no `<input type="date">`, no bare password inputs, no stray `console.log` in the apps.
- Secrets are not in the repo; `.dev.vars` is ignored and only an example is committed.
