# Project 180: full audit

Date: 13 November 2026. Scope: the repo as it is on disk (branch `feature/swaps-weigh-ins-progress`, commit `a908f02` plus 34 uncommitted files, which include the new chat). This replaces the audit of 10 November; everything that audit marked as done was re-checked only where this one touches it.

The question behind this audit: **is this ready to hand to paying clients, and will it hold up as the number of clients grows?**

## Short answer

- **Privacy and access control: good.** I found no way for a client to see another client's data, or for a coach to reach another coach's clients. That includes the new workout review, likes and comments, and chat.
- **Database design: sound.** Tables are normalised, history is snapshotted, "one per" rules are enforced by the database. A handful of gaps are listed below; none needs a table rebuild.
- **Scale: fine for a first group of about 20 to 50 clients, not yet beyond that.** Three things will actually break as numbers grow (findings 1 to 3), and they break in the admin, not in the phone app. A client's own screens only ever read that client's data, which is the right shape.
- **Release hygiene: not ready.** The work is not pushed, the newest tests have not been seen passing, and the live database is not set up.

## How this was done, and what it doesn't cover

- I read the whole database schema, the three newest migrations, every file in `packages/api/src` that builds a list or loops over people, the auth and middleware code, both Worker configs, the CI file, and the admin pages that list people.
- **Nothing was run.** The tests, Biome and the Cloudflare runtime only run on the Mac. Every finding comes from reading the code. Findings 1 and 2 are arithmetic against Cloudflare's published limits and are very likely right, but a test should confirm each.
- I did not look at any screen, so layout, dark mode and phone width are not covered.
- I did not re-read all of the UI code, the seed data or the exercise photo licences.

## Fix before real clients

### 1. The Workouts and Programs lists stop loading once the library passes 100 items: DONE (13 Nov)

**What was done:**

- `loadWorkoutExercises`, `loadWorkoutGroups`, `clientNames` (`workouts.ts`) and `loadProgramDays` (`programs.ts`) now split their id lists with `inChunks`, so every caller is safe, not only the two list pages.
- `GET /programs` counts workout days in SQL (only days with a workout, within the program's length) instead of loading every day of every program.
- The same split in the other places that passed a literal id list: the sync route's enrollment ids (up to 200), the "copies of this program" check, workouts dropped into a client's copy, and the two deletes of client workout copies (a new `chunk` helper in `batch.ts`, so each delete stays inside one batch).
- Test in `scale.test.ts`: 120 workouts and 105 programs; both lists load, with exercise counts and workout-day counts right.
- Not yet verified by running: needs `bun run check` on the Mac.


Cloudflare D1 allows at most 100 bound values in one SQL statement. Several queries pass a whole list of ids in one statement with no splitting:

- `GET /workouts` (`routes/workouts.ts`): `loadWorkoutExercises`, `loadWorkoutGroups` and `clientNames` each take every workout id on the page.
- `GET /programs` (`routes/programs.ts`): `loadProgramDays` takes every program id.
- `POST /programs/:id/sync`: accepts up to 200 enrollment ids and puts them in one statement.

With more than about 100 library workouts (an owner sees every coach's), the Workouts page answers "Something went wrong" and stays that way. The project already has the fix: `inChunks` in `batch.ts`, used by the overview. Route these through it, and add a test that creates 120 workouts.

The Programs list also loads every day of every program just to show a summary (a 52-week program is up to 364 rows). Count days in SQL instead.

### 2. Updating clients' copies of a program does not scale past a few clients: DONE (13 Nov)

**What was done:**

- `syncClientCopies` (`programs.ts`) updates any number of copies in a fixed number of round trips: it reads everything first (copies, library programs, schedules, workouts, their rows and groups, the clients' current workout copies), makes the new workout copies in one batch to learn their ids, then writes everything else in one batch (workout contents, schedules, names, removing copies no longer used). If that batch fails, the new copies are deleted again, so each client is either fully updated or untouched. `syncClientCopy` (one client, used by "assign again") calls it.
- Schedules are written several days per statement (an upsert by week and day), and slots the library dropped become rest days in one statement per client. Day rows keep their ids, so logged sessions still point at them.
- The "is each of these your client?" check is one query instead of one per person.
- `sendPush` now reaches everyone it is given (it stopped at 90), and removes dead phones in one batch.
- `overwriteWorkoutCopy` is gone (nothing else used it).
- Tests in `sync.test.ts`: 25 clients updated at once (new sets, a dropped workout, a new one, day ids kept, the unused copy deleted, nobody left "behind"), and a coach who sends one client that isn't hers gets 404 with nobody changed.
- Note: for very large updates (hundreds of clients on a big program) the second batch gets long. It is still one query for D1's limit, but if it ever comes near the 30-second limit, split it into a batch per group of clients.
- Not yet verified by running: needs `bun run check` on the Mac.


`POST /programs/:id/sync` loops over the chosen clients one at a time, and for each client runs about 5 queries plus about 4 per workout (`syncClientCopy`, `overwriteWorkoutCopy`, `copyWorkoutForClient`).

- A program with 10 workouts is roughly 45 queries per client.
- Cloudflare allows 50 queries per request on the free plan and 1,000 on the paid plan. So: one client already reaches the free limit, and about 20 clients reach the paid limit.
- It is not all-or-nothing. If it fails half-way, some clients have the new version and some the old, and the coach only sees an error.

The assign path was already rewritten into two batches (audit of 10 Nov, finding 4). Do the same here: read everything first, then write all clients' changes in one or two `db.batch` calls. A batch counts as one query.

`sendPush` also only notifies the first 90 people it is given (`userIds.slice(0, 90)`), silently. Chunk it.

### 3. The People page loads everything about every client at once: DONE (13 Nov)

**What was done:**

Each row carries a one-line summary for that page only: current program, last workout, and for coaches how many clients they coach. Six queries whatever the head count. A coach gets only their own clients whatever tab they ask for.

Opening a row shows the actions (progress, message, coach, password, delete) and the details (profile, devices, program), which load only then. 100 clients now costs one request, not about 300 plus 100 a minute.

- Tests in `people.test.ts`: paging and tab counts, search (including `%` and `_`), a coach never sees another coach's clients through any tab, clients get 403, and the program and last-workout summary.
- Not yet verified by running: needs `bun run check` on the Mac, and a look at the page at 375px and 1440px.


`apps/admin/src/routes/_dash/users.tsx` draws a full card for every client, and each card makes three requests of its own (profile, activity, program progress). The activity request repeats every 60 seconds.

- 100 clients means about 300 requests when the page opens, then 100 a minute for as long as it stays open.
- `GET /admin/users` returns every person with no paging or search on the server.

This is the screen a coach leaves open all day. Change it to a plain list (name, coach, last seen, program, one line of status) from one request, with search and paging on the server, and load the detail only when a person is opened. ## Fix soon (before about 100 clients)

### 6. The overview and inbox grow with the total number of clients: PARTLY DONE (13 Nov)

**What was done:**

- The sidebar's unread badge (`/admin/chat/unread`) is one count query (`unreadForStaff` in `chat.ts`) instead of building the whole inbox every minute.
- `GET /enrollments?status=active` filters on the server, and every admin screen asks for that (none of them showed past programs from this list).
- Test in `housekeeping.test.ts` for the status filter; the unread badge is covered by `chat.test.ts`.

**Left on purpose:** a per-client summary row for the overview. At the numbers expected this year the overview is fine; build it when clients approach a few hundred.


The project rule is that queries scale with one person's data. Three admin queries scale with everyone's:

- **Overview** (`admin-overview.ts`): loads every client's full program calendar and a week of sessions with their sets, and refreshes every 60 seconds. It stays within the query limit thanks to `inChunks`, but the rows read grow with clients × program length. Fine at 50 clients; at several hundred, keep a small per-client summary row that is updated when a workout finishes, and read that.
- **Chat inbox** (`chat.ts`, `inbox`): three queries over every client's messages every 20 seconds. The sidebar's unread badge (`/admin/chat/unread`) recomputes the whole inbox each minute just to add up one number; give it its own count query.
- **`GET /enrollments`** returns every enrollment ever made for the people you manage, and the overview's "Who's on what" filters to active ones in the browser. Filter by status on the server.

### 7. Every request reads the sign-in session from the database: DONE (13 Nov)

**What was done:**

- Better Auth's cookie cache is on when `SESSION_CACHE_SECONDS` is set: 60 seconds on the live and dev Workers, off locally and in tests (so the sign-out tests still see sign-outs at once).
- `requireUser` sends Better Auth's refreshed cookies back to the browser (without that the cache would never be renewed), asks the database again whenever the cached user still has a temporary password (so choosing one takes effect at once), and remembers when it last wrote "last seen" so a cached old time doesn't cause a write on every call.
- Trade-off (in the README): signing someone out, resetting their password or deleting them takes up to a minute to bite.


Better Auth's `cookieCache` is still off (carried over from the last audit). Each API call costs one or two extra database reads before it does any work. With chat checking every 4 seconds, the bell every 2 minutes and the admin refreshing lists, this is now the largest share of database traffic. Turn on a short cookie cache (a few minutes). The trade-off: signing someone out from the admin takes up to that long to bite.

### 8. No limit on how fast someone can call the API: DONE (13 Nov)

**What was done:**

- Two Workers rate-limit bindings on both apps (live and dev, separate counters): `API_LIMIT`, 300 calls a minute per signed-in person, checked in `requireUser`; `SEND_LIMIT`, 20 chat messages or coach likes and comments a minute per person (`assertCanSend` in `rate-limit.ts`). Over the limit answers 429.
- Counts are approximate and per Cloudflare location (Cloudflare's own description); they stop floods, not normal use. Without the binding (local, tests) nothing is limited, and a limiter that errors never blocks anyone.
- Not covered by a test: the bindings don't exist in the test Worker.


Only sign-in is limited. A signed-in client could post chat messages in a loop (each one stored for ever), and a coach account could send likes and comments in a loop (each one a push to a phone). Better Auth's own limiter keeps its counts in memory, which does not work on Workers. Add a Cloudflare rate-limiting rule on `/api/*` per IP, and a per-person cap on chat messages and feedback (the Workers rate-limit binding does this without a database write).

### 9. Database gaps (all fixable with a new index or column, no rebuild): DONE (13 Nov) except the set_logs rule

**What was done:**

- Schema: a unique index allowing one `in_progress` workout per person, and indexes on `workout_sessions.program_day_id`, `enrollments.assigned_by`, `exercise_alternatives.alternative_id` and `.created_by`. **Migration generated (13 Nov, `0014_session_links.sql`); apply it with `bun run db:apply`.** It closes any duplicate workouts in progress first, so the unique index can't fail. If it fails on the unique index, a database already holds two workouts in progress for one person; close the older with `UPDATE workout_sessions SET status = 'abandoned' WHERE status = 'in_progress' AND id NOT IN (SELECT max(id) FROM workout_sessions WHERE status = 'in_progress' GROUP BY user_id)` and run it again.
- Starting a workout closes the old one and creates the new one in one batch; the same start sent twice at once answers with the first.
- Daily cleanup (`cleanup.ts`, a cron trigger on the phone app Worker at 02:00 UTC): expired sign-ins and verification tokens, wrong-password counters over a day old that lock nobody out, and workouts in progress for over a day (closed as abandoned).
- Tests in `housekeeping.test.ts`: starting twice leaves one in progress and the database refuses a second; the cleanup closes a two-day-old workout, removes the expired sign-in and the old counter, and leaves today's workout alone.
- **Not done:** the one-row-per-set unique index on `set_logs`. It needs a check of existing data first; low risk today.


- **One workout in progress per person is only enforced in code.** Starting a workout abandons the old one and inserts the new one in two separate steps, so two taps at the same moment can leave two in progress. Add a unique index on `workout_sessions (user_id) where status = 'in_progress'`, like the one for active enrollments.
- **Foreign keys without an index.** The rule is to index every one. Missing: `workout_sessions.program_day_id`, `enrollments.assigned_by`, `exercise_alternatives.alternative_id` and `.created_by`. The first one matters: with foreign keys on, removing a program day makes SQLite scan the whole sessions table to check nothing points at it.
- **`workouts.source_workout_id` and `programs.source_program_id` are plain numbers**, not foreign keys, so the database cannot stop a copy pointing at a library item that no longer exists. The code copes ("The library program is gone"), so this is a note, not a bug. Adding the key later would need a table rebuild, so leave it and keep the code checks.
- **`set_logs` has no "one row per set" rule.** Only the phone's `client_uuid` is unique, so two different ids can both claim set 2 of the same exercise. Low risk today; a unique index on `(session_id, exercise_id, set_number, is_warmup)` would close it, but check existing data for duplicates first.
- **Nothing is ever cleaned up:** expired sign-in sessions, old `sign_in_attempts` rows, and workouts left "in progress" for days. Add a daily scheduled Worker (a cron trigger) that removes expired rows and marks stale workouts abandoned.

### 10. Opening a workout reads the person's whole lifting history: DONE (13 Nov)

**What was done:** `previousSets` finds the latest finished session per exercise in SQL (one row per exercise), then reads only those sessions' sets, instead of fetching up to 1,000 sets and sorting them in the Worker. Covered by the existing "last time" tests.


`previousSets` (`routes/sessions.ts`) fetches up to 1,000 past sets for the workout's exercises, sorted by date, and keeps only the latest session per exercise. It scales with one person, which is right, but it grows every week they train, and it runs on every open. The coach's live workout panel re-runs it every 10 seconds while a client trains. Find the latest session per exercise in SQL first, and leave "last time" out of the live refresh.

## Later (hundreds of active clients)

- **Chat by polling.** Each open chat is 15 requests a minute. That is fine into the hundreds of clients, since few have chat open at once. Past that, move to a WebSocket per conversation (Durable Objects).
- **One database, one query at a time.** D1 runs a single query at a time per database. Cloudflare's guide: about 1,000 queries a second if each takes 1 ms, about 10 a second if each takes 100 ms. Fast, indexed queries are what keep this safe, which is why findings 6, 7 and 10 matter. Read replicas exist if reads ever outgrow this.
- **Database size.** The limit is 10 GB on the paid plan. Set logs and messages are small rows; this is years away at realistic numbers, but worth a yearly look.

## Low

- `GET /exercises` returns every exercise with no paging. Fine for hundreds; add search on the server past that.
- Photo uploads trust the file type the browser reports. They are served with `nosniff` under random names, so the risk is small; checking the first bytes would close it.
- Better Auth's own `/api/auth/update-user` lets a signed-in person change their name without going through our validation (`PATCH /me`). Block the route or validate there.
- `unreadFeedback` looks through all of a client's workouts to find unread items, every 2 minutes. Small today; a `client_id` column on `session_feedback` with an index on unread rows would make it a direct lookup.
- The two largest screens (admin workout editor, phone workout screen) are still over 1,000 lines each.
- There is still no end-to-end test that signs in and logs a workout through the real screens.
- `body_checkins.photo_key` and the body-measurement columns are in the table but nothing writes them. Fine to keep if they are planned; otherwise they are noise.

## What is done well

- Access rules live in two small files (`access.ts`, `library.ts`) and every route that touches another person goes through them. "Not yours" answers 404.
- The new features kept the pattern: a coach reaches a workout or a chat only through `managedPerson`; a client's chat never takes a client id from the request; only the author can delete feedback.
- Normalised schema. The only copies are the intended ones (session snapshots, clients' program copies). Lists that are queried have their own tables.
- "One per" rules are in the database: one active program per person, one weigh-in per day, one like per coach per exercise, one read position per person per chat.
- Retried requests are safe: sessions, sets, weigh-ins and chat messages all carry an id made on the device.
- Deleting a person removes everything of theirs in one batch, and the new chat and feedback tables are covered by cascades.
- No migration rebuilds a table. Migrations 0011 to 0013 only create tables and indexes.
- Dev and local email can only reach the developer's address, with a second safety net behind it.
- CSRF check, a strict Content-Security-Policy, HSTS, no public sign-up, a sign-in limit, expiring temporary passwords.
- The phone app's own screens (plan, workout, progress, chat) each read one person's data in a fixed number of queries.
