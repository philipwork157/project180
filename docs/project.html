At a glance

Two apps on Cloudflare sharing one API and one database.

Phone app (PWA)Clients and people on their own: training, food, water, progress, coach chat.
Live project180.co.za · Dev dev.project180.co.za · Local :5173
Admin dashboardCoaches and owners manage clients and the library; the platform admin's Platform page.
Live admin.project180.co.za · Dev admin-dev.project180.co.za · Local :5174
APIHono on Cloudflare Workers at /api in both apps (each app has its own Worker and sign-in cookie). Locally the admin proxies /api to :5173.
DatabaseCloudflare D1 (SQLite), one database shared by both Workers. Drizzle ORM and migrations.

The starter library

A normal business the platform admin picks on the Platform page. People on their own read its exercises, recipes and programs. Every coach who signs up gets their own copy of its exercises, recipes and workouts. Fill it by signing in as one of its coaches, or with bun run db:seed -- --business "Starter library".

Sign-up and accounts

  • Sign-up: name, email, password twice, agree to the terms and privacy policy, Turnstile. App: someone on their own. Admin: a coach with a new business.
  • Confirm email: a one-time link (48 hours). Sign-in refuses unconfirmed accounts and offers a new link.
  • Forgot password: a one-time link (60 minutes) in both apps; signs out everywhere.
  • Welcome wizard (/welcome): only for people who signed up themselves. Goal, about you, daily plan; skippable.
  • Delete my account: Profile in the app (clients), with their password. Owners delete people from the client page.
  • Invitations: Clients → Invite client sends an email (link works 14 days). Someone new opens /invite in the app and chooses a password (signed in at once, no wizard). Someone already training on their own sees the invitation on Today; accepting moves them into the business with all their history. Pending invitations show on the Clients page with Resend and Cancel.
  • Temporary passwords: still possible ("Add with a password"); staff-set passwords must be changed at first sign-in.
  • Download my data: Profile in the app, one JSON file of everything they logged (GET /me/export).
  • Limits: 5 wrong passwords per email / 20 per network per 15 minutes; 5 sign-ups per network per hour; 3 emails per address and 10 per network per hour.
  • Terms and privacy: /terms and /privacy in both apps (draft text in packages/ui/src/legal.tsx; have it checked by a lawyer).

Database and migrations

  • Change packages/db/src/schema, then bun run db:apply. Never hand-edit a generated migration; one-off data moves are custom migrations (drizzle-kit generate --custom).
  • Never rebuild a table on D1 (a __new_ table in the SQL): it can cascade-delete child rows. Add nullable columns, new tables or indexes instead.
  • D1 takes at most 100 values per statement: multi-row inserts use insertMany + runAll.
  • Latest migrations: 0031_claude_calls, 0032_food_extras, 0033_businesses, 0034_businesses_backfill (moves the original gym into "Project 180"), 0035_email_tokens, 0036_onboarding, 0037_terms, 0038_records (invitations, who-did-what record, errors), 0039_sign_ins.

Deploying

bun run check          # everything green first
bun run deploy:dev     # dev: migrations + both apps

First time on a site: bun run admin:create:dev (or :live), pick the starter library on the Platform page, then seed it with bun run db:seed:dev -- --business "Starter library" and db:recipes:dev the same way.

Going live checklist

Everything the live site needs, once. Live keys are always new ones: never reuse a dev key on live. Secrets go on both Workers with the same value: run each command in apps/app and again in apps/admin (no --env means live).

1. Cloudflare

  • Plan: starting on the free plan. Its limits: 100,000 requests a day (both apps and dev together), 10 ms of CPU per request, 50 database queries per request, 5 million rows read and 100,000 written a day, 500 MB per database, 7 days of restore points, 5 scheduled jobs per account (we use 4: two live, two dev). When a daily limit is hit, that kind of request fails until 02:00 (midnight UTC). Move to Workers Paid ($5 a month) when real clients rely on it or sign-ins show "exceeded CPU" errors.
  • Live database: cd apps/app && bunx wrangler d1 create project180-db, then paste the printed id into database_id at the top of both apps/app/wrangler.jsonc and apps/admin/wrangler.jsonc (it's 00000000-… now).
  • Photo storage: bunx wrangler r2 bucket create project180-media.
  • Domains: project180.co.za and admin.project180.co.za are created on the first deploy (the zone must be in this Cloudflare account).
  • Turnstile: a "Project 180 live" widget for project180.co.za and admin.project180.co.za.
  • Web Analytics: if it's switched on for the zone, Cloudflare adds a script the security settings block (a console error, nothing breaks). Turn off its automatic setup, or ask to allow it.

2. Amazon SES (email)

  • Production access in af-south-1 (Cape Town): leaving the sandbox is per region, so check it's that one.
  • project180.co.za verified as a domain in af-south-1, with its DKIM records in Cloudflare DNS (plus SPF and a DMARC record so mail lands in inboxes).
  • A new IAM user for live with only ses:SendEmail; its access key pair becomes the two AWS secrets below.

Keeping an eye on things

  • Errors (Platform page): every crash in the API, every email that didn't send and every failed scheduled job is saved for 30 days. With 10 errors in 15 minutes, the platform admin gets an email (at most once an hour). Code: packages/api/src/error-log.ts.
  • Who did what (Platform page): sign-ups, email confirmations, password resets, invitations, people added, deleted, blocked or moved to another coach, temporary passwords, sign-in lockouts and platform setting changes. Names only (no emails), never training, food or chats. Code: packages/api/src/audit.ts; labels in AUDIT_ACTIONS (shared).
  • Sign-ins (Platform page): every try to sign in to the phone app and the admin, right or wrong: email, name when there's an account, what happened (signed in, wrong password, no account, locked out, blocked, email not confirmed…), device, network address and country. Filters for app and "only failed", search by email, and the networks with the most failed tries in 24 hours. Kept 90 days. Code: packages/api/src/sign-in-log.ts.
  • Database (Platform page): every table's row count and the size against D1's 10 GB, never the rows. To look at rows use the Cloudflare dashboard (D1 → project180-db) or bunx wrangler d1 execute project180-db --remote --command "…".
  • First steps (admin Today): a new coach's checklist (client, program, assign, message), ticked from what they've done, hideable.

Tests and checks

  • Unit tests: packages/shared/src/*.test.ts (dates, calories, Claude prices…).
  • API tests: packages/api/test/*.test.ts run the real Worker with a real database. Privacy tests for every resource, including businesses.test.ts (two businesses never see each other), platform.test.ts and account.test.ts.
  • End to end: apps/*/e2e with Playwright (bun run e2e).
  • Before every commit: Lefthook runs Biome and the type checks.
